`validateResource` now validates `Encounter`, `Procedure` and `DocumentReference` against their R4 4.0.1 element definitions with no schema supplied. Before, these three were not modeled: a document of one of them drew a single informational `RESOURCE_NOT_MODELED` and read `valid: true` however wrong it was. Now each has a built-in table naming every direct element with its cardinality and datatypes, so a document of one of them reports `UNKNOWN_ELEMENT` for a property R4 does not define (a warning, an error under `mode: "strict"`), `CARDINALITY_MIN` for a missing `Encounter.status` or `Encounter.class`, `Procedure.status` or `Procedure.subject`, or `DocumentReference.status` or `DocumentReference.content`, `CARDINALITY_MAX`, `TYPE_MISMATCH`, `CHOICE_AMBIGUOUS` for two variants of `Procedure.performed[x]`, and `CODE_INVALID` for a code outside the required value set of `Encounter.status`, `Procedure.status`, `DocumentReference.status` or `DocumentReference.docStatus`. The R4 base constraints run on them too (`dom-2` to `dom-5`, `ele-1`, `ext-1`; R4 declares no constraint of its own on these three types), and a `status` of `entered-in-error` on one of them is reported `RETRACTED_RESOURCE` at `information`, as it is on the safety-critical types. The safety readout is unchanged: it still lists these types on `notAssessed`. What a caller must change: a document of these types that read `valid: true` can now read `valid: false`; fix the document, or pass your own table for the type in `schemas` to replace the built-in one.
