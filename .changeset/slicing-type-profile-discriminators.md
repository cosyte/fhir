Profile validation now decides `type` and `profile` slicing discriminators where the document holds the answer, so their slices' own constraints are checked. Before, every such slicing was reported `PROFILE_SLICE_UNCHECKED` and nothing under its slices was checked.

This is a behaviour change: a document validated against a profile that slices by `type` or `profile` can now draw findings it did not draw before, such as `PROFILE_SLICE_UNMATCHED` under a closed slicing, a slice's `CARDINALITY_MIN`, or a fixed, pattern or cardinality finding on a slice's member. US Core's smoking-status profile is one: it slices `Observation.effective[x]` (6.1.0) and `Observation.value[x]` (9.0.0) by type.

- A `type` discriminator is decided from the occurrence's concrete type: a choice element's suffix (`valueQuantity` is a `Quantity`) or a resource's `resourceType`, at the discriminator path or through a trailing `resolve()`.
- A `profile` discriminator is decided for a resource held in place (a `contained` resource, a Bundle entry's `resource`) or reached by `resolve()` through the resource's `contained` set or, when the resource is a Bundle, its entries. The resource is checked against the profile the slice names, from the `profiles` you pass or from `resolveBase`, with every layer `validateResource` runs, the profile's own invariants included: an error there means it does not conform. It conforms only when every constraint the profile places on an element present in the resource is of a kind a layer enforces (cardinality, fixed and pattern values, slicing, invariants, a binding to exactly the R4 value set the schema enumerates there, a type read from the occurrence itself); any other kind, such as a narrowed `value[x]`, a `targetProfile`, `maxLength`, `minValue[x]`, `maxValue[x]`, a binding to another value set or an invariant on a slice itself, leaves the slicing `PROFILE_SLICE_UNCHECKED` with `profile-undecided`.
- A `type` or `profile` discriminator path that selects more than one node in an occurrence decides nothing (`path-unsupported`), rather than matching when any one of them does.
- A slicing that still cannot be decided stays `PROFILE_SLICE_UNCHECKED`, and the finding now says why in `sliceReason`, one of the new `SLICE_UNCHECKED_REASONS`: a reference that leaves the closure (`target-unresolved`; no server is ever fetched), a profile you did not supply (`profile-unavailable`), the R5 `position` discriminator (`discriminator-unsupported`), and the rest. Nested profile checks are bounded at eight deep and 4096 per validation.

`matchSlices` takes an optional fourth argument, a `SliceContext` (each occurrence's choice type, reference resolution and profile conformance), and its result carries `reason` when it is unchecked. `collectProfileIssues` and `collectInvariantIssues` take `profiles` in their options, and `validateResource` passes its own. `SliceDefinition` has an optional `types`, `validationIssue` an optional sixth parameter, `sliceReason`, `ElementDefinition` an optional `unmodeled` (what a definition states that the model does not read), and `RequiredBinding` an optional `valueSet`.

What a caller must change: nothing to keep compiling. A pipeline that treats a profile-validated document as valid should expect new findings on profiles that slice by `type` or `profile`. To have a `profile` discriminator decided, pass the profile the slice names in `profiles`.
